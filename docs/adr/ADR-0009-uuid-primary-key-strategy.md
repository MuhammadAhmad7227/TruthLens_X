# ADR-0009 — UUIDv7 for append-only event tables, UUIDv4 elsewhere

| | |
|---|---|
| **Status** | Accepted — ratified 2026-11-10 |
| **Decision ID** | D-009 |
| **Related** | [DATABASE_DESIGN §2.4](../DATABASE_DESIGN.md), [ADR-0004](ADR-0004-single-organisation-tenancy-with-capability-rbac.md) |

## Context

Identifiers appear in URLs, audit records and exported reports. Two properties conflict: **index
locality** (sequential ids keep B-tree inserts cheap) and **unguessability** (a client must not be
able to enumerate another case's evidence by incrementing an id).

## Decision

1. **UUIDv7** (time-ordered) for append-only, high-volume event tables: `audit_logs`,
   `custody_events`, `model_invocations`, `integrity_checks`, `detections`, `transcript_segments`,
   `derivatives`, `analysis_jobs`. Generated by a custom PL/pgSQL function using `pg_random_bytes`.
2. **UUIDv4** (fully random) for entity tables: `users`, `cases`, `evidence_items`,
   `physical_objects`, `ai_models`, `reports`.
3. No sequential integer primary key is exposed in any API path.
4. `citext` for email columns; native PostgreSQL enums for stable value sets and `text` + `CHECK`
   for sets expected to grow.

## Alternatives considered

| Option | Verdict |
|---|---|
| BIGSERIAL everywhere | Rejected — trivially enumerable, leaks case volume, and complicates future multi-tenancy. |
| UUIDv4 everywhere | Rejected for event tables — random inserts fragment B-tree indexes on the highest-volume tables. |
| ULID / Snowflake | Viable, but UUIDv7 is native to PostgreSQL 18-era tooling and needs no application-side clock coordination. |

## Rationale

Event tables are insert-dominated and benefit from time ordering; entity tables are read-dominated
and benefit from maximum unguessability. Matching the id version to the access pattern gets both.

## Consequences

* UUIDv7 ids embed a **creation timestamp**. That is acceptable for internal event tables but is why
  entity tables use v4 — a `case_id` must not disclose when a case was opened.
* The generator function is part of the migration baseline and must never be redefined incompatibly.

## Licensing implications

None — PL/pgSQL, first-party.

## Security implications

Non-enumerable entity ids are a real control: combined with ADR-0004's 404-on-denial, an attacker
cannot discover case or evidence identifiers by probing.

## Reversal strategy

Id types are fixed at table creation; changing later requires a migration and URL compatibility
shims. The decision is cheap to make now and expensive to reverse, which is why it is an ADR.

## Verification

* Migration test asserts column types (`uuid`) and that the generator produces monotonically
  increasing values for v7 tables.
* A test asserts v7 ids decode to a timestamp within a tolerance of insert time.
* No API path accepts or returns an integer id (contract test against the OpenAPI baseline).
